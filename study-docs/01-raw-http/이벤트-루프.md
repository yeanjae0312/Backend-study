# 이벤트 루프: 같은 3초인데 하나는 서버를 멈춘다

대상 코드: `01-raw-http/server.ts`에 추가할 `GET /block`과 `GET /wait`. 아직 코드가 없다. 개념은 HTTP-기초.md 10절에 있으니 이 문서는 **실험**만 다룬다. 코드를 넣고 나면 줄 번호를 채운다.
목표: "동기로 기다리면 전부 멈추고, 비동기로 기다리면 안 멈춘다"를 두 엔드포인트로 나란히 본다.

---

## 1. 실험 코드

`/visits` 블록 아래에 넣는다. 둘 다 `?ms=3000` 같은 쿼리로 시간을 받는다.

```ts
    // 이벤트 루프 실험. 둘 다 3초 걸리지만 서버에 미치는 영향이 정반대다. 실험 후 지운다.
    const ms = Number(url.searchParams.get("ms")) || 3000;
    if (url.pathname === "/block") {
      const end = Date.now() + ms;
      while (Date.now() < end) {} // 스레드를 붙잡는다. 이 동안 다른 요청은 콜백조차 시작 못 한다
      return send(res, 200, { blocked: ms });
    }
    if (url.pathname === "/wait") {
      await setTimeout(ms); // 스레드를 놓아준다. 타이머가 끝나면 이 줄 다음부터 재개
      return send(res, 200, { waited: ms });
    }
```

`setTimeout`은 `node:timers/promises`의 것이다. 파일 위에 import를 추가한다.

```ts
import { setTimeout } from "node:timers/promises";
```

전역 `setTimeout(콜백, ms)`와 이름이 같지만 다른 함수다. 이쪽은 Promise를 돌려줘서 `await`로 쓴다. check.ts가 이미 `sleep`이라는 이름으로 쓰고 있다.

`url.searchParams`는 처음 쓴다. 62줄에서 `new URL`로 감쌌기 때문에 `?ms=3000`이 `searchParams.get("ms")`로 나온다. HTTP-기초.md 8절.

---

## 2. 해보기 1: `/block`은 전부 멈춘다

REST Client 탭 두 개, 또는 REST Client와 브라우저.

1. `GET http://localhost:4000/block?ms=5000`을 보낸다.
2. **바로** 다른 탭에서 `GET http://localhost:4000/notes`를 보낸다.
3. `/notes`도 5초 뒤에 온다. 터미널 1을 보면 `GET /notes` 로그조차 5초 뒤에 찍힌다. 요청은 소켓에 도착했지만 콜백을 실행할 스레드가 `while`에 잡혀 있어서다.
4. Ctrl+C를 눌러 본다. 5초가 끝나기 전에는 "shutting down"도 안 찍힌다. SIGINT 핸들러도 콜백이라 차례를 못 받는다.

이게 "Node에서 동기로 무거운 일을 하면 안 된다"의 실체다. `while`이 아니어도 같다. 큰 JSON 파싱, 동기 파일 읽기(`readFileSync`), 암호 해싱(동기 API), 정규식 폭주(ReDoS). Phase 4에서 비밀번호 해시에 argon2의 **비동기** API를 쓰는 이유다.

---

## 3. 해보기 2: `/wait`은 안 멈춘다

1. `GET /wait?ms=5000`을 보낸다.
2. 바로 `GET /notes`. **즉시** 온다. 터미널에도 `GET /notes`가 바로 찍힌다.
3. `/wait`을 다섯 개 동시에 보내도 전부 5초 뒤에 **동시에** 온다. 25초가 아니다.

`await`가 하는 일: "타이머 끝나면 여기부터 다시 실행해 줘"라고 등록만 하고 스레드를 놓는다. 그 사이 이벤트 루프는 다른 요청의 콜백을 돈다. DB 쿼리, 외부 API 호출, 파일 읽기가 전부 이 모양이라 Node 서버는 스레드 하나로 수천 연결을 받는다.

같은 3초, 같은 코드 길이인데 서버에 미치는 영향이 반대다. 차이는 **기다리는 동안 스레드를 쥐고 있느냐**뿐이다.

---

## 4. 해보기 3: `readJson`도 같은 원리

이미 있는 코드에서 확인한다. 71줄 `await readJson(req)`.

1. REST Client로 큰 바디를 POST하는 대신, 터미널에서 바디를 천천히 보낸다. PowerShell:
   ```
   $c = New-Object Net.Sockets.TcpClient("localhost", 4000); $s = $c.GetStream(); $w = New-Object IO.StreamWriter($s)
   $w.Write("POST /notes HTTP/1.1`r`nHost: localhost`r`nContent-Length: 40`r`n`r`n"); $w.Flush()
   ```
   바디는 아직 안 보냈다. 서버는 `end` 이벤트를 기다리는 중이다.
2. 이 상태에서 REST Client로 `GET /notes`. 즉시 온다. 바디를 기다리는 동안 스레드가 놓여 있다는 뜻이다.
3. `$w.Write('{"title":"slow","content":"slow body"}'); $w.Flush()`로 바디를 마저 보내면 201이 온다. `$c.Close()`.

60줄 콜백이 `async`인 이유가 이것이다. 바디가 다 올 때까지 동기로 기다렸다면 느린 클라이언트 하나가 서버를 멈춘다.

## 6. Spring에서는

**여기가 Node와 가장 다른 지점이다.** 같은 실험을 Spring에서 하면 결과가 다르다.

- `/block`에 해당하는 `Thread.sleep(5000)`이나 `while` 루프를 컨트롤러에 넣어도 **다른 요청은 멈추지 않는다.** 요청마다 스레드가 따로라서 그 요청의 스레드만 잠든다. Tomcat 기본 최대 200개.
- 그래서 Spring 코드에는 `/wait`에 해당하는 것이 따로 없다. 그냥 블로킹으로 쓴다. DB 호출도 `repository.findAll()`이 돌아올 때까지 그 스레드가 멈춰 있고, 아무도 신경 안 쓴다. 회사 코드에 `async`, `await`가 없는 이유다.
- 대신 **스레드가 바닥나면** Node의 `/block`과 같은 현상이 난다. 재현하려면 `application.yml`에 `server.tomcat.threads.max: 1`을 주고 `Thread.sleep(5000)` 엔드포인트를 부른 뒤 다른 요청을 보내면 된다. 스레드가 하나뿐이니 Node처럼 전부 멈춘다. 실제 장애에서는 200개가 느린 DB 쿼리에 전부 묶이는 식으로 일어난다. "DB가 느려지니 헬스체크까지 죽어서 컨테이너가 재시작됐다"는 장애가 이 원리다.
- 그래서 Spring에서 볼 것은 "동기 코드가 있나"가 아니라 **"타임아웃이 있나"**다. `RestTemplate`/`WebClient`의 connect·read 타임아웃, JDBC의 `queryTimeout`, HikariCP의 `connectionTimeout`. 타임아웃 없는 외부 호출 하나가 스레드 200개를 전부 묶을 수 있다. Claude Code가 생성한 코드에서 외부 호출을 보면 타임아웃부터 찾는다.
- 비동기가 필요하면 `@Async`(다른 스레드 풀로 넘김)나 WebFlux(Node 같은 이벤트 루프 모델)를 쓰지만 일반 MVC 프로젝트에서는 드물다.

### Nest에서는

Node이므로 server.ts와 완전히 같다. 컨트롤러 메서드 안의 `while`은 서버 전체를 멈춘다. 무거운 CPU 작업은 Phase 7의 BullMQ 워커(별도 프로세스)로 보낸다. 그게 Nest에서 "다른 스레드로 넘기는" 방법이다.
