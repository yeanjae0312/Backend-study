# 쿠키: server.ts의 `/visits`와 같이 읽기

대상 코드: `01-raw-http/server.ts`의 `readCookies`(55~63줄)와 `GET /visits`(77~83줄), `check.ts`의 쿠키 단언, `requests.http`의 10~11번. 줄 번호는 2026-11-11 기준.
읽는 법: HTTP-기초.md 9절의 미리보기를 먼저 읽고, 이 문서는 코드를 돌려 보면서 따라간다. 목표는 "쿠키는 헤더 두 줄이고, 믿을 수 없는 값이며, 서버는 아무것도 기억하지 않는다"를 손으로 확인하는 것.

---

## 1. 쿠키가 필요한 이유

HTTP는 요청마다 독립이다(HTTP-기초 1절). 서버는 "방금 온 요청"만 보고 "아까 그 사람"은 모른다. 그래서 서버가 클라이언트에게 표식을 주고, 클라이언트가 매 요청에 그 표식을 다시 들고 오게 한다. 그 표식이 쿠키다.

핵심은 **기억하는 쪽이 브라우저**라는 것. 서버는 "이거 들고 다녀"라고 한 번 말하고 잊는다. `/visits`가 방문 횟수를 세지만 server.ts 어디에도 횟수를 저장하는 변수가 없는 이유다.

**코드에서:** 80줄. `readCookies(req).visits`로 읽어 1을 더하고 바로 돌려보낸다. 두 요청 사이에 서버가 가진 상태는 없다.

**해보기:** 서버를 띄우고 requests.http 10번을 세 번 누른다. 응답 바디의 `visits`가 1, 2, 3. 그 상태에서 서버를 껐다 켜고 다시 누르면 4다. 서버를 재시작해도 이어지는 건, 숫자가 서버가 아니라 REST Client(브라우저 역할) 쪽에 있기 때문이다. `notes`는 재시작하면 사라지는 것과 비교해 보자.

---

## 2. 쿠키는 헤더 두 줄이다

```
# 응답 (서버 → 브라우저). "이거 보관해"
Set-Cookie: visits=1; Path=/; Max-Age=3600; HttpOnly; SameSite=Lax

# 다음 요청 (브라우저 → 서버). 브라우저가 자동으로 붙인다. 속성은 안 돌아온다
Cookie: visits=1
```

주의할 비대칭 하나. 응답에는 속성(`Path`, `Max-Age`, ...)이 붙지만 요청에는 `이름=값`만 온다. 속성은 "브라우저가 보관할 때 지킬 규칙"이지 서버에 되돌려 줄 정보가 아니다. 그래서 서버는 자기가 준 쿠키가 언제 만료되는지 요청만 보고는 알 수 없다.

쿠키가 여러 개면 요청에는 `"; "`로 이어 붙어 한 줄로 온다.

```
Cookie: visits=3; theme=dark; won.customer.device=abc
```

**코드에서:** 55~63줄 `readCookies`. `"; "`로 쪼개고, 각 조각을 첫 `"="`에서 이름과 값으로 나눈다. 9줄이 전부다. 쓰기는 81줄 `res.setHeader("set-cookie", ...)`. `send`가 `writeHead`를 부르기 전에 걸어 두면 헤더에 합쳐진다. 405의 `allow` 헤더와 같은 방식이다.

**해보기:** 10번 응답 패널에서 `set-cookie` 헤더를 찾는다. 속성까지 다 보인다. 그다음 브라우저에서 `localhost:4000/visits`를 열고 개발자 도구 Network 탭에서 요청 헤더의 `cookie`를 본다. `visits=N`만 있고 속성은 없다.

## 3. 속성: 브라우저에게 주는 보관 규칙

| 속성 | 뜻 | 빼면 |
|---|---|---|
| `Path=/` | 이 경로 아래 요청에만 붙인다 | 기본값은 쿠키를 준 경로의 디렉터리. `/visits`에서 주면 `/visits`에만 붙고 `/notes`에는 안 붙는다 |
| `Max-Age=3600` | 3600초 뒤 브라우저가 버린다 | 세션 쿠키. 브라우저를 닫으면 사라진다 |
| `HttpOnly` | `document.cookie`로 못 읽는다 | XSS로 심긴 스크립트가 쿠키를 읽어 밖으로 보낼 수 있다 |
| `SameSite=Lax` | 다른 사이트에서 시작된 POST에는 안 붙인다 | 다른 사이트의 `<form>`이 내 서버에 쿠키를 실어 POST할 수 있다(CSRF) |
| `Secure` | HTTPS에서만 보낸다 | HTTP로 보내면 중간에서 읽힌다. 지금은 http라 안 붙였다. Phase 9에서 붙인다 |
| `Domain` | 서브도메인까지 공유 | 기본은 준 호스트에만 |

쿠키를 **지우는** 방법은 따로 없다. 같은 이름으로 `Max-Age=0`을 다시 주면 브라우저가 즉시 버린다. 로그아웃이 이것이다.

**해보기:**

1. 브라우저에서 `/visits`를 몇 번 새로고침하고 개발자 도구 Application → Cookies → localhost에서 `visits` 행을 본다. HttpOnly 체크, SameSite Lax, Expires 시각이 보인다.
2. 콘솔에 `document.cookie`를 친다. `visits`가 안 보인다. HttpOnly 때문이다.
3. 81줄에서 `HttpOnly`를 지우고 서버를 재시작한 뒤 다시 2번. 이번엔 보인다. 되돌린다.
4. 81줄에서 `Max-Age=3600`을 `Max-Age=0`으로 바꾸고 새로고침. Application 탭에서 쿠키가 사라진다. 다음 새로고침은 다시 1부터다. 되돌린다.
5. 81줄에서 `Path=/`를 지우고 새로고침한 뒤 `/notes`를 연다. Network 탭에서 `/notes` 요청에는 `cookie`가 없다.

## 4. 쿠키는 믿을 수 없는 값이다

쿠키는 클라이언트가 보관하고 클라이언트가 보낸다. 그러니 클라이언트가 바꿀 수 있다. 서버는 받은 값이 자기가 준 값인지 알 방법이 없다.

**코드에서:** 80줄은 `visits`가 숫자가 아니면 0으로 취급한다(`Number(...) || 0`). 방어는 그게 전부다. 999를 보내면 1000을 돌려준다.

**해보기:** requests.http 11번. `Cookie: visits=999`를 직접 보내면 1000이 온다. 브라우저에서도 Application 탭에서 값을 더블클릭해 바꿀 수 있다.

이것이 **쿠키에 사용자 ID를 직접 넣으면 안 되는 이유**다. `userId=1`을 `userId=2`로 바꾸는 순간 남이 된다. 해법은 두 가지다.

- **세션 ID** (Phase 4에서 만든다): 쿠키에는 추측 불가능한 랜덤 문자열만 넣는다(`sid=8f3a...`). 사용자 정보는 서버의 세션 저장소(메모리 → Redis)에 두고, 매 요청마다 `sid`로 찾는다. 값을 바꾸면 "그런 세션 없음"이 될 뿐이다.
- **서명** (Phase 7의 JWT): 값과 함께 서버만 아는 키로 만든 서명을 붙인다. 값을 바꾸면 서명이 안 맞는다. 서버가 저장소 없이 검증할 수 있는 대신, 한번 준 토큰을 만료 전에 무효화하기 어렵다.

둘 다 "쿠키 자체는 믿지 않는다"에서 출발한다.

---

## 5. 쿠키 헤더에는 남의 것도 섞여 온다

쿠키는 **호스트** 기준이고 포트를 보지 않는다. `localhost:3000`의 앱이 준 쿠키가 `localhost:4000`에도 붙어서 온다. HTTP-기초를 하며 `console.log(req.headers)`에서 봤던 `won.customer.device`가 그것이다. 브라우저 확장이 넣는 쿠키도 있다.

따라서 파서는 **모르는 값에 관대**해야 한다. 내가 안 쓰는 쿠키의 형식이 이상하다고 내 엔드포인트가 죽으면 안 된다.

**코드에서:** 59~60줄. 처음 버전은 값을 `decodeURIComponent`로 풀었는데, 다른 앱 쿠키에 `%E0%` 같은 깨진 퍼센트 인코딩이 있으면 그 함수가 예외를 던져 `/visits`가 500이 됐다. 지금은 값을 그대로 둔다. `check.ts`의 두 번째 쿠키 요청이 `other=%E0%; visits=1; junk`를 섞어 보내 이걸 확인한다.

**해보기:** 60줄을 `decodeURIComponent(pair.slice(i + 1))`로 되돌리고 `node check.ts`를 돌려 본다. 실패한다. 다시 되돌린다. "리뷰어가 잡은 버그를 테스트가 지키는" 흐름을 한 번 겪어 두자.

## 6. 쿠키와 fetch

브라우저의 `fetch`는 같은 출처면 쿠키를 자동으로 붙인다. 다른 출처(포트가 달라도)면 `credentials: "include"`를 줘야 붙이고, 서버는 `Access-Control-Allow-Credentials: true`를 돌려줘야 한다. 이건 다음 CORS 묶음에서 깨뜨려 본다.

Node의 `fetch`는 쿠키를 **아예 기억하지 않는다**. 브라우저가 아니라서 쿠키 저장소가 없다. 그래서 check.ts는 두 번째 요청에 `cookie` 헤더를 손으로 넣는다. 서버 간 통신에서 쿠키 기반 인증이 불편한 이유이기도 하다.

**코드에서:** check.ts의 쿠키 단언. 첫 응답의 `set-cookie`가 `visits=1;` 로 시작하는지, 그 값을 손으로 실어 보내면 2가 되는지.

## 7. 프레임워크에서는

### Spring에서는

- 읽기: 컨트롤러 메서드 인자에 `@CookieValue("visits") String visits`. 없으면 400이 나므로 `required = false` 또는 `defaultValue = "0"`을 쓴다. `readCookies` + `Number(...) || 0`이 이 한 줄이다.
- 쓰기: `ResponseCookie.from("visits", "2").path("/").maxAge(3600).httpOnly(true).sameSite("Lax").build()`를 만들어 `ResponseEntity.ok().header(HttpHeaders.SET_COOKIE, cookie.toString())`. 81줄의 문자열을 빌더로 만드는 것뿐이다.
- 실무에서는 쿠키를 직접 쓰는 코드가 드물다. Spring Security가 `JSESSIONID` 쿠키로 세션을 관리하고, 속성은 `application.yml`의 `server.servlet.session.cookie.http-only`, `.same-site`, `.secure`로 정한다. JWT를 쓰는 곳은 쿠키 대신 `Authorization` 헤더를 받는다.
- 회사 코드에서 찾아볼 것: `CookieValue`, `ResponseCookie`, `session.cookie`로 전체 검색. 아무것도 안 나오면 세션 쿠키는 전부 Security 기본 설정이다.

### Nest에서는

- `cookie-parser` 미들웨어를 `app.use(cookieParser())`로 등록하면 `req.cookies.visits`로 읽는다. `readCookies`가 정확히 이 미들웨어가 하는 일이다.
- 쓰기는 `@Res({ passthrough: true }) res`를 받아 `res.cookie("visits", 2, { path: "/", maxAge: 3600_000, httpOnly: true, sameSite: "lax" })`. `maxAge`가 **밀리초**인 것만 조심한다(Set-Cookie 헤더는 초).
- Phase 4에서 세션 쿠키 가드를 만들 때 `req.cookies.sid`를 읽어 저장소에서 사용자를 찾는 코드가 이 문서 4절의 세션 ID 그대로다.

### Express에서는

Nest와 같은 `cookie-parser`, 같은 `res.cookie()`. Nest가 밑에서 Express를 쓰기 때문이다.

## 8. 자기 점검

코드를 안 보고 답할 수 있으면 쿠키 부분은 끝이다.

1. `/visits`의 방문 횟수는 어디에 저장되는가? 서버를 재시작하면 어떻게 되는가?
   - 브라우저(또는 REST Client)의 쿠키 저장소에 있다. 서버에는 변수가 없다. 그래서 서버를 재시작해도 횟수가 이어진다. `notes` 배열은 서버 메모리라 재시작하면 사라지는 것과 반대다.

2. 요청의 `Cookie` 헤더에는 `Max-Age`가 왜 안 오는가?
   - 속성은 "브라우저가 보관할 때 지킬 규칙"이지 서버에 돌려줄 정보가 아니다. 브라우저는 규칙대로 보관하다가 요청에는 `이름=값`만 붙인다. 그래서 서버는 요청만 보고는 자기가 준 쿠키가 언제 만료되는지 알 수 없다.

3. `HttpOnly`가 막는 공격과 `SameSite=Lax`가 막는 공격은 각각 무엇인가?
   - `HttpOnly`는 **XSS**. 심긴 스크립트가 `document.cookie`로 세션 쿠키를 읽어 밖으로 보내는 걸 막는다.
   - `SameSite=Lax`는 **CSRF**. 다른 사이트의 `<form>`이나 스크립트가 내 서버로 POST를 날릴 때 브라우저가 쿠키를 안 붙인다. "다른 도메인을 허용할지"가 아니라 "다른 사이트에서 **시작된** 요청에 쿠키를 실을지"다. 링크 클릭 같은 GET 이동에는 붙는다(그래서 Lax).

4. 쿠키를 지우려면 어떻게 하는가?
   - 같은 이름으로 `Max-Age=0`(또는 과거 `Expires`)을 다시 준다. 브라우저가 즉시 버린다. 로그아웃이 이것이다.

5. 쿠키에 `userId=1`을 직접 넣으면 무슨 일이 생기고, 세션 ID는 그걸 어떻게 피하는가?
   - 클라이언트가 값을 바꿀 수 있고 서버는 받은 값이 자기가 준 값인지 알 수 없으므로, `userId=2`로 바꾸는 순간 남이 된다.
   - 세션 ID는 **암호화가 아니다**. 추측 불가능한 랜덤 문자열을 쿠키에 넣고, 사용자 정보는 서버 저장소에 둔다. 값을 바꾸면 "그런 세션 없음"이 될 뿐이다. 값에 서명을 붙여 위조를 막는 쪽은 JWT(Phase 7)다.

6. `localhost:3000`의 앱이 준 쿠키가 `localhost:4000`에 오는 이유는?
   - 쿠키는 **호스트** 기준이고 **포트를 보지 않는다**. `localhost`면 포트가 달라도 같은 쿠키 저장소다. SameSite와는 무관하다. SameSite는 "어느 사이트에서 시작된 요청인가"를 보는데, 둘 다 `localhost`라 같은 사이트다.

7. 처음 `readCookies`가 500을 낸 원인은 무엇이고, 왜 쿠키 파서는 모르는 값에 관대해야 하는가?
   - `decodeURIComponent`가 다른 앱 쿠키의 깨진 퍼센트 인코딩(`%E0%`)을 만나 예외를 던졌다. 쿠키 헤더에는 같은 호스트의 다른 앱, 브라우저 확장, 사용자가 손으로 넣은 값이 섞여 오므로, 내가 안 쓰는 쿠키의 형식 때문에 내 엔드포인트가 죽으면 안 된다.

8. Node의 `fetch`로 `/visits`를 두 번 부르면 왜 둘 다 1이 나오는가?
   - Node의 `fetch`에는 쿠키 저장소가 없다. 첫 응답의 `set-cookie`를 기억하지 않으니 두 번째 요청에 `cookie` 헤더가 안 붙고, 서버는 매번 0+1을 돌려준다. 브라우저가 아니라서가 맞고, 정확히는 "브라우저가 해 주던 쿠키 보관이 없어서"다. 그래서 check.ts는 두 번째 요청에 쿠키를 손으로 싣는다.

9. (Spring) `@CookieValue`로 없는 쿠키를 읽으면 기본으로 무슨 일이 생기고, 어떻게 막는가?
   - 기본이 `required = true`라 `MissingRequestCookieException`이 나고 400으로 응답한다. `@CookieValue(value = "visits", required = false)` 또는 `defaultValue = "0"`을 준다. server.ts의 `Number(...) || 0`이 `defaultValue = "0"`에 해당한다.

10. (Spring) 회사 서버의 세션 쿠키 속성은 어디서 정해지는가?
    - `application.yml`의 `server.servlet.session.cookie.*`(`http-only`, `secure`, `same-site`, `max-age`, `name`). 코드에서 쿠키를 직접 만들지 않는 한 Spring Security가 `JSESSIONID`를 이 설정대로 만든다. 설정이 없으면 Servlet 컨테이너 기본값(HttpOnly 켜짐, SameSite 없음, Secure 꺼짐)이다.
