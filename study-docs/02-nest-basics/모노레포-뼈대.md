# 모노레포 뼈대: pnpm 워크스페이스가 패키지를 잇는 방법

대상 코드: `nest-lab/` 루트의 `package.json`, `pnpm-workspace.yaml`, `eslint.config.mjs`, `.prettierrc`, `.env.example`과 `packages/config`, `packages/shared`. 2026-11-18 기준.
읽는 법: 파일마다 주석을 달아 두었다. 이 문서는 "왜 이 파일이 있는지"와 "직접 깨뜨려 보는 실험"이다. 파일 열 개가 전부라 한 시간이면 된다.

## 2. 워크스페이스: 폴더 둘을 하나의 설치로

`pnpm-workspace.yaml`의 글롭 아래에 `package.json`이 있으면 그 폴더가 **워크스페이스 패키지**다. 루트에서 `pnpm install` 한 번이면 전부 설치되고, 패키지끼리는 `workspace:*`로 참조한다.

```json
// packages/shared/package.json
"devDependencies": { "@nest-lab/config": "workspace:*" }
```

이 한 줄로 pnpm 은 npm 레지스트리에 가지 않고 `packages/config` 폴더를 **심볼릭 링크**로 `packages/shared/node_modules/@nest-lab/config`에 건다. 그래서 `tsconfig.json`의 `"extends": "@nest-lab/config/tsconfig.base.json"`이 풀린다. config 를 고치면 shared 에 즉시 반영된다. 복사가 아니라 링크라서.

**해보기:**
1. `ls -la packages/shared/node_modules/@nest-lab/` → `config -> ../../../config` 링크가 보인다.
2. `pnpm-workspace.yaml`에서 `packages/*` 줄을 지우고 `pnpm install`. shared 가 `@nest-lab/config`를 레지스트리에서 찾다 실패한다. 되돌리고 다시 install.
3. `pnpm -r typecheck`의 `-r`은 recursive. 모든 패키지에서 그 스크립트를 찾아 돈다. 스크립트가 없는 config 는 건너뛴다. 출력 첫 줄 "Scope: 2 of 3 workspace projects"의 3은 루트+config+shared 다.
4. `pnpm --filter @nest-lab/shared build`. 하나만 고를 때. 2-3 부터 `pnpm --filter api start:dev`로 계속 쓴다.

## 3. pnpm 의 node_modules: 호이스팅이 없다

npm 과 yarn classic 은 모든 의존성을 루트 `node_modules`에 **평평하게 끌어올린다**(호이스팅). 편하지만 부작용이 있다. 내가 `package.json`에 안 적은 패키지도 어쩌다 거기 있으면 `import` 가 된다. 이걸 **유령 의존성**이라 한다. 어느 날 남의 패키지가 그 의존성을 버리면 내 코드가 이유 없이 깨진다.

pnpm 은 다르다.

```
node_modules/
├── .pnpm/                  실제 파일은 전부 여기. 114개 (설치된 모든 패키지의 모든 버전)
│   ├── eslint@9.39.5/
│   ├── typescript@5.9.3/
│   └── ...
├── eslint -> .pnpm/eslint@9.39.5/node_modules/eslint      내가 적은 것만 링크
├── prettier -> ...
├── typescript -> ...
└── typescript-eslint -> ...
```

루트 `node_modules`에는 **내가 `package.json`에 적은 다섯 개만** 보인다. 나머지 109개는 `.pnpm` 안에 있고 각 패키지가 자기 의존성을 거기서 링크로 찾는다. 안 적은 패키지는 import 가 안 된다. 그게 의도다.

**해보기:**
1. `ls node_modules` → 다섯 개. `ls node_modules/.pnpm | wc -l` → 114.
2. shared 의 `src/index.ts`에 `import "semver";`를 추가하고 `pnpm typecheck`. semver 는 eslint 가 쓰므로 `.pnpm` 안에 **있지만** shared 는 못 찾는다. 에러. 이것이 유령 의존성 차단이다. npm 이었다면 조용히 통과했을 것이다. 되돌린다.
3. 같은 패키지의 다른 버전 둘이 필요하면 `.pnpm/x@1.0.0`과 `.pnpm/x@2.0.0`이 공존한다. 디스크는 전역 스토어(`pnpm store path`)에 한 번만 저장되고 하드링크라 프로젝트가 열 개여도 용량은 한 번이다.

## 4. dependencies 세 종류

| 필드 | 뜻 | 이 프로젝트에서 |
|---|---|---|
| `dependencies` | 런타임에 필요. 배포되는 코드가 import 한다 | 2-3 에서 `@nestjs/core` 등 |
| `devDependencies` | 개발·빌드·테스트에만 필요 | 루트의 typescript, eslint, prettier, @types/node |
| `peerDependencies` | "이 패키지를 쓰려면 네가 X 를 깔아야 한다". 플러그인이 호스트를 지목할 때 | typescript-eslint 가 eslint 와 typescript 를 peer 로 요구한다 |

루트에 devDependencies 를 두는 이유: typescript 버전이 패키지마다 다르면 타입이 어긋난다. 도구는 루트에 한 벌, 런타임 의존성은 각 앱에. 2-3 에서 `apps/api`를 만들면 Nest 패키지는 거기 `dependencies`로 들어간다.

`packageManager: "pnpm@11.15.1"` 필드는 Node 의 corepack 과 pnpm 자신이 읽어서 다른 버전으로 설치하려 하면 막는다. lock 파일 포맷이 버전마다 달라서 팀원이 다른 pnpm 을 쓰면 lock 이 매번 바뀐다. 그걸 막는 한 줄이다.

**해보기:** `cat pnpm-lock.yaml | head -30`. 루트와 shared 가 importer 로 나뉘어 있고 각각이 무엇을 어느 버전으로 받았는지 적혀 있다. lock 은 "다음 사람도 정확히 이 버전을 받게" 하는 파일이라 **커밋한다**.

## 5. 패키지가 자기를 설명하는 방법: main, types, exports

`packages/shared/package.json`:

```json
"main": "./dist/index.js",         // require("@nest-lab/shared") 가 여는 파일 (옛 방식, 아직 널리 읽힘)
"types": "./dist/index.d.ts",      // TS 가 타입을 읽는 파일
"exports": {                       // 새 방식. 어느 경로를 어떤 조건에서 어떤 파일로 줄지
  ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" }
},
"files": ["dist"]                  // publish 할 때 포함할 것. private 라 지금은 문서 역할
```

`exports`가 있으면 그 밖의 경로(`@nest-lab/shared/src/index.ts` 같은)는 **막힌다**. 패키지 내부 구조를 숨기는 장치다. base 의 `moduleResolution: nodenext`는 Node 와 똑같이 `exports`를 먼저 읽는다. `main`/`types`는 `exports`를 모르는 옛 도구를 위해 같이 둔다. (2026-11-23 수정: 처음엔 `node10`이었는데 Nest 12 가 ESM 전용이라 `nodenext`로 바꿨다. TS 6 에서 `node10`은 deprecated 이기도 하다.)

왜 `src/index.ts`를 바로 가리키지 않고 `dist`를 거치나. Nest 의 tsc 빌드는 `rootDir` 밖의 `.ts`를 컴파일 대상으로 받으면 TS6059 에러를 낸다. 심볼릭 링크를 따라가면 `packages/shared/src`는 `apps/api`의 rootDir 밖이다. 그래서 shared 는 먼저 `dist`로 빌드하고 api 는 그 산출물을 쓴다. "shared 를 고치면 build 를 다시 해야 한다"는 불편이 생기는데, Phase 5 의 Turborepo 가 의존 순서대로 빌드를 자동으로 돌려 준다.

**해보기:** `"types"` 줄을 지우고 `pnpm build` 후 어딘가에서 import 해 보려 해도 지금은 소비자가 없다. 2-3 에서 api 가 `import type { Note } from "@nest-lab/shared"`를 쓰기 시작하면 그때 지워 보자. 타입이 `any`로 떨어진다.

## 6. tsconfig.base.json: 옵션마다 이유

파일 안 주석에 적혀 있다. 여기서는 셋만 다시.

- **`module: nodenext`.** (2026-11-23 수정. 처음엔 `commonjs`였다.) 모듈 시스템은 둘이다. CommonJS 는 `require()`로 불러오는 옛 방식, ESM 은 `import`가 런타임까지 남는 표준 방식. Nest 11 까지는 CommonJS 가 기본이었는데 **Nest 12 부터 패키지가 ESM 전용**이라 프로젝트도 ESM 이다(`package.json`의 `"type": "module"`). `nodenext`는 "Node 가 하는 그대로 해석해라"는 뜻이라 상대 import 에 `.js` 확장자를 붙여야 하고(`./app.module.js`), `__dirname` 대신 `import.meta.dirname`을 쓴다. Phase 1 의 `node server.ts`도 ESM 이었으니 같은 모양이다. 회사나 블로그의 Nest 코드에 `require`가 보이면 11 이하다.
- **`experimentalDecorators` + `emitDecoratorMetadata`.** `@Controller()`, `@Injectable()`은 TS 의 데코레이터 문법이고, 두 번째 옵션은 생성자 인자의 **타입**을 JS 에 메타데이터로 남긴다. Nest DI 가 "이 생성자는 NotesService 를 달라고 한다"를 아는 방법이 이것이다. Node 의 타입 스트리핑은 타입을 **지우기만** 해서 메타데이터가 안 나온다. 그래서 Phase 1 은 `node server.ts`였고 Nest 는 `tsc` 빌드다.
- **`forceConsistentCasingInFileNames`.** Windows 는 `Notes.ts`와 `notes.ts`를 같은 파일로 보고 Linux 는 다른 파일로 본다. 로컬(Windows)에서 되던 import 가 CI 나 배포(Linux)에서 깨지는 가장 흔한 이유다. 켜면 로컬에서 미리 잡는다.

**해보기:** base 에서 `"strict": true`를 지우고 `src/index.ts`에 `export const f = (x) => x;`를 넣어 `pnpm typecheck`. 통과한다(`x`가 암묵적 `any`). strict 를 되돌리면 에러. 되돌린다.

## 7. 린트와 포맷은 루트 한 벌

계획서에는 "config 패키지에서 공유"라고 적었는데 그러지 않았다. ESLint 9 의 flat config 와 Prettier 는 **현재 폴더에서 위로 올라가며** 설정 파일을 찾는다. 루트에 하나 두면 하위 패키지 어디서 돌려도 같은 규칙이다. 패키지로 만들어 각자 import 하게 하는 건 지금 필요 없는 간접 계층이다. Next 가 들어와 react 규칙이 필요해지면 `apps/web/eslint.config.mjs`를 따로 둔다.

둘의 역할 차이. **Prettier 는 모양**(들여쓰기, 따옴표, 줄 길이)만 바꾸고 의미는 안 본다. **ESLint 는 의미**(안 쓰는 변수, `any`, 잘못된 비교)를 본다. 겹치는 부분은 Prettier 에 맡기고 ESLint 는 모양 규칙을 끄는 것이 관례다. `typescript-eslint`의 `recommended`가 그렇게 돼 있다.

**해보기:** `src/index.ts`에 `const unused = 1;`을 넣고 `pnpm lint`. `no-unused-vars` 경고. `pnpm format` 은 그 줄을 그대로 둔다(모양은 멀쩡하니까). 되돌린다.

## 8. .env.example

`.env`는 비밀이 들어가므로 gitignore 다. 그러면 새로 clone 한 사람은 어떤 변수가 필요한지 모른다. `.env.example`은 **이름 목록**이다. 값은 로컬 기본값이거나 비워 둔다. 복사해서 `.env`를 만든다. Phase 5 의 `@nestjs/config`가 이 파일을 읽고 스키마로 검증하게 된다. 지금은 `PORT` 하나.

## 9. 프레임워크·실무에서는

### Spring에서는

- 모노레포 ↔ **Gradle 멀티 프로젝트**. 루트 `settings.gradle`의 `include("api", "shared")`가 `pnpm-workspace.yaml`이고, `api/build.gradle`의 `implementation(project(":shared"))`가 `workspace:*`다. 회사 저장소 루트에 `settings.gradle`이 있으면 열어 보자. 모듈 목록이 거기 있다.
- `package.json`의 `dependencies` ↔ `build.gradle`의 `implementation`. `devDependencies` ↔ `testImplementation`, `compileOnly`. `peerDependencies`에 해당하는 것은 없고 BOM(`spring-boot-dependencies`)이 버전을 한 곳에서 맞춘다.
- `pnpm-lock.yaml` ↔ Gradle 은 기본으로 lock 을 안 만든다. `dependencyLocking`을 켜야 생긴다. 회사 코드에 `gradle.lockfile`이 없으면 빌드마다 버전이 미세하게 달라질 수 있다는 뜻이다.
- `tsconfig.base.json` ↔ 루트 `build.gradle`의 `subprojects { ... }` 블록. Java 버전, 컴파일 옵션을 거기서 공유한다.
- 유령 의존성 ↔ Gradle 도 `implementation`은 **전이 의존성을 컴파일 클래스패스에 안 올린다**(`api`와 달리). 같은 문제를 같은 방식으로 막는다.
- ESLint/Prettier ↔ Checkstyle, Spotless. 회사에서 `spotlessApply`를 돌리라는 말이 `pnpm format`이다.
- `.env.example` ↔ `application.yml` + `application-local.yml`(gitignore). Spring 은 환경변수보다 프로파일별 yml 을 더 쓴다.

### 이 뼈대 위에 올라올 것

- 2-3: `apps/api`(Nest). 루트 devDependencies 의 typescript 를 쓰고, `tsconfig.json`이 base 를 extends 하고, `@nest-lab/shared`를 `workspace:*`로 받는다.
- Phase 5: Turborepo. `pnpm -r build`가 의존 순서를 모르고 알파벳순으로 돌리는 문제를 `turbo.json`의 `dependsOn: ["^build"]`가 푼다.
- Phase 6: `apps/web`(Next). 자기 tsconfig 에서 `module`, `moduleResolution`, `jsx`를 덮어쓴다.

## 10. 자기 점검

1. `pnpm-workspace.yaml`은 무엇을 정하는 파일인가? 글롭 하나를 지우면 무슨 일이 생기는가?
   - "어느 폴더가 워크스페이스 패키지인가"를 정한다. 글롭 아래에 `package.json`이 있는 폴더가 패키지다. `packages/*`를 지우면 config 와 shared 가 패키지로 인식되지 않아, shared 의 `@nest-lab/config: workspace:*`를 레지스트리에서 찾다가 install 이 실패한다.

2. `workspace:*`를 쓰면 pnpm 이 레지스트리 대신 무엇을 하는가? 그래서 config 를 고치면 shared 에 언제 반영되는가?
   - 같은 워크스페이스의 폴더를 `node_modules/@nest-lab/config`에 **심볼릭 링크**로 건다. 복사가 아니라 링크라서 config 를 고치면 **즉시** 반영된다. 다시 install 할 필요가 없다.

3. 호이스팅이 무엇이고 유령 의존성은 왜 생기는가? pnpm 은 그걸 어떻게 막는가?
   - 호이스팅은 모든 의존성(전이 의존성 포함)을 루트 `node_modules`에 평평하게 끌어올리는 것. 그러면 내 `package.json`에 안 적은 패키지도 거기 있어서 import 가 되는데, 그게 유령 의존성이다. 남의 패키지가 그 의존성을 버리면 내 코드가 이유 없이 깨진다. pnpm 은 루트 `node_modules`에 **내가 적은 것만** 링크로 두고 나머지는 `.pnpm` 안에 격리해서, 안 적은 패키지는 import 가 안 되게 한다.

4. 루트 `node_modules`에 다섯 개만 보이는데 `.pnpm`에 114개가 있는 이유는?
   - 다섯 개는 루트 `package.json`에 적은 직접 의존성이고, 114개는 그것들이 끌고 오는 전이 의존성까지 전부다. 실제 파일은 `.pnpm` 에만 있고, 각 패키지는 자기 의존성을 거기서 링크로 찾는다. 같은 패키지의 다른 버전도 `.pnpm/x@1.0.0`, `.pnpm/x@2.0.0`으로 공존한다.

5. `dependencies`와 `devDependencies`를 나누는 기준은? 루트에 devDependencies 를 두는 이유는?
   - 배포되는 코드가 런타임에 import 하면 `dependencies`, 개발·빌드·테스트에만 쓰면 `devDependencies`. 루트에 두는 이유는 typescript, eslint 같은 도구는 **버전이 하나**여야 패키지끼리 타입과 규칙이 어긋나지 않기 때문이다. 런타임 의존성(Nest 패키지)은 쓰는 앱에만 둔다.

6. `packageManager` 필드와 `pnpm-lock.yaml`은 각각 무엇을 막는가?
   - `packageManager`는 다른 버전의 pnpm 으로 설치하는 것을 막는다. lock 포맷이 버전마다 달라 팀원마다 lock 이 바뀌는 것을 방지한다. `pnpm-lock.yaml`은 다음 사람이 **다른 버전의 패키지**를 받는 것을 막는다. `^9.0.0` 같은 범위가 아니라 실제 설치된 정확한 버전을 적어 두므로 커밋한다.

7. `main`, `types`, `exports`는 각각 누가 읽는가? `exports`가 있으면 무엇이 막히는가?
   - `exports`는 Node 와 새 해석(`nodenext`, `bundler`)이 **먼저** 읽으며 경로별·조건별로 파일을 지정한다. `main`은 `exports`를 모르는 옛 도구와 옛 해석(`node10`)이 여는 파일, `types`는 그때 TS 가 타입을 읽는 파일. 둘은 호환용이다. `exports`가 있으면 거기 적지 않은 경로(`@nest-lab/shared/src/index.ts` 등)로의 import 가 **막힌다**. 내부 구조를 숨기는 장치다.

8. shared 가 `src/index.ts`를 바로 노출하지 않고 `dist`를 거치는 이유는?
   - Nest 의 tsc 빌드는 `rootDir` 밖의 `.ts`를 컴파일 대상으로 받으면 TS6059 에러를 낸다. 심볼릭 링크를 따라가면 `packages/shared/src`는 `apps/api`의 rootDir 밖이다. 그래서 shared 를 먼저 `dist`(js + d.ts)로 빌드하고 api 는 산출물만 쓴다. 대가로 "shared 를 고치면 다시 build" 가 필요하고, Phase 5 의 Turborepo 가 이 순서를 자동으로 돌린다.

9. `emitDecoratorMetadata`가 남기는 것은 무엇이고, Node 타입 스트리핑으로는 왜 안 되는가?
   - 생성자 인자와 프로퍼티의 **타입 정보**를 JS 에 메타데이터(`design:paramtypes` 등)로 남긴다. Nest DI 는 이걸 읽어 "이 생성자는 NotesService 를 달라고 한다"를 안다. Node 의 타입 스트리핑은 타입 표기를 **지우기만** 하고 아무것도 남기지 않으므로 DI 가 무엇을 주입할지 알 수 없다. 그래서 Phase 1 은 `node server.ts`로 됐지만 Nest 는 `tsc` 빌드가 필요하다.

10. `forceConsistentCasingInFileNames`가 막는 사고는 어떤 환경 조합에서 나는가?
    - 로컬이 Windows(또는 macOS 기본)이고 CI·배포가 Linux 일 때. Windows 는 `Notes.ts`와 `notes.ts`를 같은 파일로 보지만 Linux 는 다른 파일로 본다. 로컬에서 대소문자가 틀린 import 가 통과했다가 Linux 에서 "모듈 없음"으로 터진다. 켜 두면 로컬에서 미리 에러가 난다.

11. Prettier 와 ESLint 의 역할 차이는? 겹치는 부분은 어느 쪽에 맡기는가?
    - Prettier 는 **모양**(들여쓰기, 따옴표, 줄 길이)만 바꾸고 의미는 안 본다. ESLint 는 **의미**(안 쓰는 변수, `any`, 잘못된 비교)를 본다. 모양 규칙이 겹치면 Prettier 에 맡기고 ESLint 의 모양 규칙은 끈다. `typescript-eslint`의 `recommended`가 이미 그렇게 돼 있다.

12. (Spring) `pnpm-workspace.yaml`과 `workspace:*`에 해당하는 Gradle 파일과 문법은?
    - 루트 `settings.gradle`의 `include("api", "shared")`가 워크스페이스 선언이고, `api/build.gradle`의 `implementation(project(":shared"))`가 `workspace:*`다. 회사 저장소 루트의 `settings.gradle`을 열면 모듈 목록이 있다.

13. (Spring) 회사 저장소에 `gradle.lockfile`이 없으면 무엇을 뜻하는가?
    - Gradle 은 기본으로 lock 을 안 만든다. `dependencyLocking`을 켜야 생긴다. 없으면 `1.2.+` 같은 동적 버전이나 전이 의존성이 빌드 시점마다 미세하게 달라질 수 있다는 뜻이다. 다만 Spring Boot 의 BOM 이 주요 버전을 고정하므로 실무에서 체감되는 일은 드물다. pnpm 의 lock 이 "기본"인 것과 대비된다.
