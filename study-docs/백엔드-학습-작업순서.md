## 0. 개요

### 목표

- 백엔드의 기본 동작(HTTP, DB, 인증, 테스트, 배포)을 **왜 그런지 설명할 수 있는 수준**으로 익힌다.
- 최종 산출물: 이메일 로그인 + 소셜 로그인이 되는 API 서버, 이를 소비하는 최소 웹 화면, 나중에 모바일 앱.
- 같은 API를 Express와 NestJS 두 번 구현해 "프레임워크가 뭘 대신 해주는지"를 비교한다.

## Phase 1. 원시 서버: `node:http` (3~5일)

### 목표

프레임워크 없이 HTTP 서버를 만들어, 이후 모든 프레임워크가 "대신 해주는 것"이 무엇인지 기준점을 세운다.

### 작업

- [ ] `node:http`로 서버 띄우기. 포트, 리스닝, 프로세스 종료(SIGINT) 처리
- [ ] URL과 메서드로 분기하는 라우터를 직접 작성 (`GET /notes`, `POST /notes`, `GET /notes/:id`)
- [ ] 요청 바디를 스트림으로 읽어 JSON 파싱. 잘못된 JSON이면 400 응답
- [ ] 응답 헤더 직접 설정 (`Content-Type`, `Content-Length`), 상태 코드 선택 (200, 201, 204, 400, 404, 405, 500)
- [ ] 메모리 배열에 데이터 저장 (DB 없이)
- [ ] 쿠키 읽기와 쓰기 (`Cookie`, `Set-Cookie` 헤더를 문자열로 직접 파싱)
- [ ] 에러를 잡아 500으로 바꾸고 프로세스가 죽지 않게 하기
- [ ] 브라우저 HTML 한 장에서 `fetch`로 호출. CORS 에러를 일부러 내고 `Access-Control-*` 헤더로 해결
- [ ] curl 또는 REST Client로 모든 엔드포인트를 호출한 기록 남기기

### 익혀야 할 개념

- HTTP 메시지 구조: 시작줄, 헤더, 빈 줄, 바디
- 요청은 스트림이다. 바디는 한 번에 오지 않는다
- 상태 코드 분류 (2xx, 3xx, 4xx, 5xx)와 각 코드의 의미
- 멱등성: GET, PUT, DELETE는 멱등, POST는 아님
- 쿠키의 속성: `HttpOnly`, `Secure`, `SameSite`, `Path`, `Max-Age`
- 동일 출처 정책과 CORS, 프리플라이트(OPTIONS)
- 이벤트 루프: 동기 코드가 길면 서버 전체가 멈추는 이유

### 완료 기준

- 라우팅, 바디 파싱, 쿠키, CORS를 라이브러리 없이 구현해서 브라우저와 curl 양쪽에서 동작한다.
- "Express가 있으면 이 코드 중 어디가 없어지는가"를 목록으로 적었다.

### 함정

- 여기서 완성도를 높이려 하지 않는다. 지저분해도 된다. 목적은 기준점이다.

## Phase 2. 모노레포 뼈대 (3~5일)

### 목표

패키지, tsconfig, 워크스페이스가 서로 어떻게 연결되는지 직접 손으로 구성한다.

### 작업

- [ ] 루트 `package.json`, `pnpm-workspace.yaml` (`apps/*`, `packages/*`)
- [ ] `packages/config`: `tsconfig.base.json` 작성. `strict`, `module`, `moduleResolution`, `target`을 각각 왜 그 값인지 주석으로
- [ ] `packages/shared`: 빈 zod 스키마 하나와 타입 export. `package.json`의 `name`, `exports`, `types` 설정
- [ ] `apps/api`: Phase 1의 원시 서버를 TypeScript로 옮겨 넣기. `tsx`로 개발 실행, `tsc`로 타입 검사 스크립트
- [ ] api에서 `workspace:*`로 shared를 의존성에 추가하고 import가 되는지 확인
- [ ] `docker-compose.yml`에 Postgres 추가, 볼륨 설정, `docker compose up -d` 후 클라이언트로 접속
- [ ] `.env.example` 작성, `.env`는 gitignore
- [ ] ESLint + Prettier를 config 패키지에서 공유

### 익혀야 할 개념

- 호이스팅과 유령 의존성. pnpm의 `node_modules/.pnpm` 구조를 직접 열어본다
- `dependencies` / `devDependencies` / `peerDependencies`의 차이와 `workspace:` 프로토콜
- `package.json`의 `main`, `exports`, `types`가 import 결과를 결정하는 방식
- ESM과 CommonJS. `"type": "module"`을 켰을 때 뭐가 달라지는지
- 트랜스파일(tsx, esbuild)과 타입 검사(tsc)는 다른 작업이다
- 락파일이 보장하는 것
- Docker 볼륨: 컨테이너를 지워도 데이터가 남는 이유

### 완료 기준

- 루트에서 `pnpm -r typecheck`, `pnpm --filter api dev`가 동작한다.
- shared의 타입을 바꾸면 api에서 타입 에러가 난다.
- Postgres에 클라이언트로 접속해 테이블을 하나 만들 수 있다.

### 함정

- Turborepo는 아직 넣지 않는다. 앱이 하나일 때는 필요가 없다.
- 패키지를 미리 쪼개지 않는다. shared, config 두 개로 시작한다.

## Phase 3. Express + raw SQL로 메모 CRUD (2~3주)

### 목표

인증 없는 단순 리소스 하나로 백엔드의 기본 동작 전부를 겪는다. 이 Phase가 가장 중요하다.

### 작업

**3-1. Express 도입 (2일)**

- [ ] Phase 1의 원시 서버를 Express로 교체. 어떤 코드가 사라졌는지 비교
- [ ] 미들웨어 체인 이해: `express.json()`, 로깅 미들웨어 직접 작성, `next()`의 역할
- [ ] 에러 핸들링 미들웨어 (인자 4개짜리), 비동기 에러가 Express 5에서 어떻게 전파되는지

**3-2. DB 연결과 raw SQL (4일)**

- [ ] `pg` 드라이버로 연결, 커넥션 풀 설정. 풀 크기를 1로 줄여 요청 두 개를 동시에 보내보기
- [ ] `notes` 테이블 설계: id(uuid 또는 bigint identity), title, content, created_at, updated_at
- [ ] 마이그레이션 파일을 SQL로 직접 작성하고 순서대로 적용하는 스크립트 (`node-pg-migrate` 또는 직접)
- [ ] 목록, 단건, 생성, 수정, 삭제를 파라미터 바인딩(`$1`)으로 작성. 문자열 연결로 쿼리를 만들어 SQL 인젝션을 재현해보고 바인딩으로 막기
- [ ] 페이지네이션: offset 방식 → 커서 방식으로 바꾸고 차이를 체감
- [ ] 정렬, 검색(`ILIKE`), 그리고 `EXPLAIN ANALYZE`로 인덱스 전후 비교
- [ ] 트랜잭션: 메모 두 개를 한 번에 만들다 중간에 실패시켜 롤백 확인

**3-3. 계층 분리와 검증 (3일)**

- [ ] `routes` → `services` → `repositories` 세 층으로 분리. 각 층이 아는 것과 모르는 것을 주석으로
- [ ] shared에 zod로 요청 스키마 정의, api에서 검증 미들웨어로 사용
- [ ] 에러 응답 형식 통일 (`{ code, message, details? }`), 에러 코드는 shared에
- [ ] 404, 400(검증 실패), 409(중복), 500 각각 언제 쓰는지 정리

**3-4. 통합 테스트 (4일)**

- [ ] Vitest 설정, testcontainers로 테스트마다 깨끗한 Postgres 띄우기
- [ ] supertest로 각 엔드포인트의 성공과 실패 케이스 테스트
- [ ] 테스트용 DB 초기화 전략 (각 테스트 전 트랜잭션 롤백 vs 테이블 비우기)
- [ ] 서비스 계층 단위 테스트 (저장소를 가짜로 바꿔서)

### 익혀야 할 개념

- 미들웨어 패턴과 요청 수명 주기
- 커넥션 풀이 왜 필요한지, 풀이 바닥나면 어떻게 되는지
- SQL 기본: SELECT, INSERT, UPDATE, DELETE, WHERE, ORDER BY, LIMIT, 인덱스, 실행 계획
- 트랜잭션과 ACID, 격리 수준의 존재 (깊이는 나중에)
- offset 페이지네이션이 느려지는 이유와 커서 방식
- 계층 분리의 목적: 교체 가능성과 테스트 가능성
- 검증은 경계에서 한 번. 내부에서는 신뢰
- 통합 테스트와 단위 테스트의 차이, 각각 뭘 보장하는지

### 완료 기준

- 메모 CRUD + 페이지네이션 + 검색이 전부 테스트로 덮여 있고 `pnpm --filter api test`가 통과한다.
- SQL 인젝션을 재현하고 막은 기록이 있다.
- 세 층의 역할을 다른 사람에게 설명할 수 있다.

### 함정

- ORM을 아직 쓰지 않는다. SQL을 손으로 쓰는 시간이 가장 오래 남는 자산이다.
- 메모에 "작성자" 컬럼을 미리 넣지 않는다. Phase 4에서 필요가 생길 때 넣는다.

## Phase 4. 인증 1차: 세션 쿠키 (2주)

### 목표

"메모를 남이 못 보게 하려면 뭐가 필요한가"에서 출발해 세션 기반 인증과 권한을 구현한다.

### 작업

**4-1. 사용자와 비밀번호 (3일)**

- [ ] `users` 테이블: id, email(unique), password_hash, created_at
- [ ] argon2로 해싱. bcrypt와의 차이, 왜 SHA-256으로 하면 안 되는지 정리
- [ ] 가입 API: 이메일 형식 검증, 중복 시 409, 비밀번호 최소 규칙
- [ ] 로그인 API: 이메일 없음과 비밀번호 틀림을 같은 메시지로 응답하는 이유

**4-2. 세션 (4일)**

- [ ] `sessions` 테이블: id(랜덤 토큰), user_id, expires_at, created_at
- [ ] 로그인 성공 시 세션 생성, `Set-Cookie`로 세션 id 전달 (`HttpOnly`, `SameSite=Lax`, 개발에선 `Secure` 제외)
- [ ] 인증 미들웨어: 쿠키에서 세션 찾고 만료 확인, `req.user` 채우기
- [ ] 로그아웃: 세션 삭제 + 쿠키 만료
- [ ] 만료된 세션 정리 스크립트
- [ ] `GET /me` 엔드포인트

**4-3. 권한 (3일)**

- [ ] `notes`에 `user_id` 추가하는 마이그레이션. 기존 데이터를 어떻게 할지 결정
- [ ] 메모 목록은 내 것만, 남의 메모 수정과 삭제는 403 vs 404 중 무엇으로 할지 결정하고 이유 적기
- [ ] 인증 필요한 라우트와 아닌 라우트를 명확히 구분

**4-4. 테스트와 보안 점검 (3일)**

- [ ] 로그인한 상태를 유지하는 테스트 헬퍼 (쿠키 전달)
- [ ] 가입, 로그인, 로그아웃, 남의 메모 접근 시도 테스트
- [ ] 로그인 시도 레이트리밋 (지금은 메모리 기반, Phase 5에서 Redis로)
- [ ] CSRF가 뭔지, `SameSite=Lax`가 어디까지 막는지 정리

### 익혀야 할 개념

- 인증(누구인가)과 인가(뭘 할 수 있는가)의 차이
- 비밀번호 해싱: 솔트, 느린 해시, 레인보우 테이블
- 세션 기반 인증의 흐름과 상태가 서버에 사는 것의 장단점
- 쿠키 속성이 보안에 미치는 영향
- 타이밍 공격과 응답 메시지로 정보가 새는 문제
- CSRF, XSS와 쿠키의 관계

### 완료 기준

- 로그인 없이는 메모를 못 보고, 로그인하면 내 메모만 보인다. 전부 테스트로 증명한다.
- 세션 방식의 장단점을 설명할 수 있고, "그럼 JWT는 언제 필요한가"에 가설을 적었다.

### 함정

- JWT, 리프레시 토큰은 아직 하지 않는다. 세션이 왜 충분한지부터 안다.
- Passport 같은 인증 라이브러리를 쓰지 않는다.

## Phase 5. 백엔드 기본기 채우기 (2~3주)

### 목표

운영 가능한 서버가 갖춰야 할 것들을 하나씩 넣으며, 각각이 없을 때의 불편을 먼저 겪는다.

### 작업

**5-1. Drizzle ORM 전환 (4일)**

- [ ] 스키마를 Drizzle로 정의, 기존 SQL 마이그레이션과 drizzle-kit 마이그레이션 관계 정리
- [ ] 저장소 계층만 Drizzle로 교체. 서비스와 라우트는 손대지 않는 게 목표
- [ ] Drizzle이 생성하는 SQL을 로그로 확인하며 raw SQL과 비교
- [ ] 관계 쿼리(users ↔ notes)와 N+1 문제 재현 후 조인으로 해결

**5-2. Redis (3일)**

- [ ] docker-compose에 Redis 추가
- [ ] 세션 저장소를 Postgres에서 Redis로 이동. TTL로 만료 처리. 왜 옮기는지 적기
- [ ] 로그인 레이트리밋을 Redis 기반으로 (슬라이딩 윈도우 또는 토큰 버킷)
- [ ] 메모 목록 캐시와 무효화 전략. 캐시 때문에 틀린 데이터가 보이는 상황을 일부러 만들기

**5-3. 로깅과 에러 (2일)**

- [ ] pino 도입, 요청마다 request id 부여, 응답 시간 기록
- [ ] 에러를 "예상한 에러(4xx)"와 "예상 못한 에러(5xx)"로 나누고 후자만 스택 로깅
- [ ] 프로세스 레벨 핸들러 (`unhandledRejection`, `uncaughtException`)와 graceful shutdown

**5-4. 문서와 설정 (2일)**

- [ ] zod 스키마에서 OpenAPI 문서 생성, Swagger UI로 확인
- [ ] 환경 변수 스키마 검증 (zod). 없으면 시작 시 바로 실패
- [ ] 헬스 체크 엔드포인트 (`/health`: DB, Redis 연결 확인)

**5-5. Turborepo 도입 (1일)**

- [ ] `turbo.json`에 `dev`, `build`, `test`, `typecheck` 정의, `dependsOn: ["^build"]` 의미 확인
- [ ] shared를 바꿨을 때 api만 다시 돌아가는지 캐시 동작 확인

### 익혀야 할 개념

- ORM이 대신 해주는 것과 숨기는 것
- 캐시 무효화가 어려운 이유, TTL과 명시적 무효화
- 인메모리 저장소가 필요한 이유 (속도, 만료, 분산 환경에서 공유)
- 구조화 로깅과 상관 관계 id
- 12-factor: 설정은 환경 변수로, 로그는 stdout으로
- 작업 그래프와 캐시 (Turborepo)

### 완료 기준

- Drizzle 전환 후 Phase 3~4 테스트가 수정 없이 통과한다.
- Redis를 끄면 헬스 체크가 실패하고, 서버가 시작 시 환경 변수 누락을 바로 알려준다.
- `/docs`에서 모든 API를 문서로 볼 수 있다.

## Phase 6. Next.js 최소 화면 (1주)

### 목표

API를 실제 브라우저 클라이언트에서 소비하며 쿠키, CORS, SameSite가 어떻게 맞물리는지 서버 쪽에서 조정한다. 프론트 비중은 여기서 대부분 소진한다.

### 작업

- [ ] `apps/web` Next.js App Router 생성. 화면은 가입, 로그인, 메모 목록, 메모 작성 네 개만
- [ ] 클라이언트 컴포넌트에서 `fetch(credentials: "include")`로 api 호출. CORS 설정을 api 쪽에서 맞추기
- [ ] 서버 컴포넌트에서 쿠키를 들고 api를 호출하는 방식 (BFF) 한 번 해보기
- [ ] 미들웨어로 비로그인 사용자를 로그인 페이지로 리다이렉트
- [ ] shared의 zod 스키마를 폼 검증에 재사용. `transpilePackages` 설정이 왜 필요한지
- [ ] 스타일은 최소. 기본 HTML 요소로 끝낸다

### 익혀야 할 개념

- 브라우저가 쿠키를 보내는 조건 (origin, SameSite, credentials)
- 서버 컴포넌트와 클라이언트 컴포넌트가 각각 어디서 실행되는지
- 같은 shared 코드가 Node와 브라우저 양쪽에서 돌아야 한다는 제약

### 완료 기준

- 브라우저에서 가입 → 로그인 → 메모 작성 → 로그아웃이 된다.
- CORS와 쿠키 문제를 서버 설정으로 해결한 기록이 있다.

### 함정

- UI를 다듬지 않는다. 프론트에 시간을 쓰기 시작하면 비중이 깨진다.

## Phase 7. 소셜 로그인, 토큰, 작업 큐 (2~3주)

### 목표

외부 인증 제공자와 연동하고, 세션을 토큰 기반으로 확장하며, 요청 밖에서 도는 작업을 다룬다.

### 작업

**7-1. Google OIDC 수동 구현 (5일)**

- [ ] Google Cloud Console에서 OAuth 클라이언트 생성, 리다이렉트 URI 등록
- [ ] 인가 코드 흐름을 라이브러리 없이: `/auth/google` → 구글 → `/auth/google/callback`
- [ ] `state` 파라미터로 CSRF 방지, PKCE(`code_verifier`, `code_challenge`) 적용
- [ ] 코드를 토큰으로 교환, `id_token`(JWT) 서명 검증 (JWKS 가져와서)
- [ ] `oauth_accounts` 테이블: provider, provider_user_id, user_id. 이메일이 같은 기존 계정과 연결하는 정책 결정
- [ ] 소셜 로그인 후에도 기존 세션 방식으로 로그인 상태 유지

**7-2. 액세스 + 리프레시 토큰 (5일)**

- [ ] 세션과 병행 가능한 토큰 발급 엔드포인트 설계 (웹은 쿠키 세션 유지, 앱용으로 토큰)
- [ ] 액세스 토큰(JWT, 짧은 만료)과 리프레시 토큰(불투명 문자열, DB 저장, 긴 만료)
- [ ] 리프레시 토큰 회전과 재사용 탐지 (훔친 토큰이 쓰이면 전체 무효화)
- [ ] JWT 검증 미들웨어, 세션 미들웨어와 공존
- [ ] 기기별 로그아웃, 전체 로그아웃

**7-3. BullMQ 작업 큐 (3일)**

- [ ] 가입 시 이메일 인증 메일 발송을 큐에 넣기 (실제 발송은 콘솔 출력 또는 Mailpit 컨테이너)
- [ ] 워커 프로세스를 api와 분리해서 실행
- [ ] 실패 재시도, 지수 백오프, 죽은 작업 확인
- [ ] 이메일 인증 토큰 검증 엔드포인트

### 익혀야 할 개념

- OAuth 2.0과 OIDC의 차이. 인가 코드 흐름의 각 단계가 왜 있는지
- `state`와 PKCE가 막는 공격
- JWT 구조, 서명 검증, 왜 JWT를 세션처럼 무효화하기 어려운지
- 리프레시 토큰 회전과 재사용 탐지
- 요청 응답 밖에서 처리해야 하는 일과 큐의 역할
- 멱등한 작업과 재시도

### 완료 기준

- 구글 로그인, 이메일 로그인 둘 다 되고 같은 사용자로 연결된다.
- 토큰 재사용 공격을 테스트로 재현하고 막는다.
- 워커를 꺼도 api는 동작하고, 켜면 밀린 작업이 처리된다.

### 함정

- 소셜 로그인 라이브러리(Auth.js, Passport)를 쓰지 않는다. 흐름을 이해한 뒤라면 나중에 교체해도 된다.
- 구글 하나만 한다. 두 번째 제공자는 패턴이 같다.

## Phase 8. NestJS 재구현 (3~4주)

### 목표

같은 API 계약을 NestJS로 다시 구현하며, 모듈과 의존성 주입이 Express에서 겪은 어떤 문제를 해결하는지 체감한다.

### 작업

**8-1. 구조 옮기기 (1주)**

- [ ] `apps/api-nest` 생성 (Express 어댑터 기본). 포트를 다르게
- [ ] 모듈 설계: `AuthModule`, `UsersModule`, `NotesModule`, `DatabaseModule`, `RedisModule`
- [ ] Express의 저장소 계층을 프로바이더로, 서비스 계층을 Nest 서비스로 옮기기
- [ ] 의존성 주입으로 저장소를 갈아끼우며 Express 때 수동으로 넘기던 것과 비교

**8-2. Nest 고유 개념 (1주)**

- [ ] 파이프로 zod 검증 (shared 스키마 재사용)
- [ ] 가드로 인증과 권한. Phase 4의 미들웨어와 비교
- [ ] 인터셉터로 로깅과 응답 변환
- [ ] 예외 필터로 에러 응답 형식 통일
- [ ] 커스텀 데코레이터 (`@CurrentUser()`)

**8-3. 계약 검증 (1주)**

- [ ] Phase 3~7의 통합 테스트를 두 서버 모두에 돌릴 수 있게 베이스 URL만 바꾸는 구조로 조정
- [ ] 테스트가 전부 통과할 때까지 맞추기
- [ ] Nest Swagger 모듈로 문서 생성, Express 쪽 OpenAPI와 비교

**8-4. 비교 정리 (2일)**

- [ ] Express 버전과 Nest 버전의 코드량, 구조, 테스트 작성 난이도 비교표
- [ ] "Nest가 강제하는 것 중 Express에서 이미 스스로 하고 있던 것"과 "새로 얻은 것" 목록
- [ ] 두 서버 중 하나를 남길지, 둘 다 남길지 결정

### 익혀야 할 개념

- 의존성 주입 컨테이너의 동작과 모듈 스코프
- 데코레이터와 메타데이터 (`reflect-metadata`)
- 요청 처리 순서: 미들웨어 → 가드 → 인터셉터 → 파이프 → 핸들러 → 인터셉터 → 예외 필터
- 프레임워크가 구조를 강제하는 것의 득과 실

### 완료 기준

- 같은 통합 테스트가 Express와 Nest 양쪽에서 통과한다.
- 비교표를 작성했고, 어느 상황에 어느 쪽을 택할지 말할 수 있다.

## Phase 9. 배포와 운영 (1~2주)

### 목표

로컬에서만 돌던 서버를 실제 환경에 올리고, 운영 중 보는 것들을 경험한다.

### 작업

- [ ] api용 Dockerfile (멀티 스테이지: 의존성 설치 → 빌드 → 실행 이미지). `pnpm deploy` 또는 `turbo prune`으로 모노레포에서 api만 추리기
- [ ] 로컬에서 이미지로 실행해 docker-compose의 Postgres, Redis와 연결
- [ ] Postgres 호스팅 (Neon 또는 Supabase) 또는 플랫폼 내장 DB, Redis 호스팅 (Upstash 등)

- [ ] 헬스 체크를 플랫폼에 연결, 로그 확인
- [ ] autocannon 등으로 간단한 부하를 걸어 커넥션 풀 크기와 인덱스 유무에 따른 응답 시간 비교

- 마이그레이션을 배포 파이프라인 어디에 두는지
- 운영 환경에서 쿠키가 깨지는 전형적 원인
- 커넥션 풀 포화, 느린 쿼리가 전체 응답에 미치는 영향

### 완료 기준

- 공개 URL에서 가입, 로그인, 구글 로그인, 메모 작성이 된다.
- 부하 테스트 전후 수치를 기록했다.

## 부록 B. 끝났을 때 설명할 수 있어야 하는 질문

- 요청 하나가 브라우저에서 출발해 DB를 거쳐 응답으로 돌아오기까지 각 단계에서 무슨 일이 일어나는가
- 세션과 JWT는 각각 언제 쓰고, 왜 JWT는 무효화가 어려운가
- 커넥션 풀이 없으면 무슨 일이 생기는가
- 인덱스는 왜 모든 컬럼에 걸지 않는가
- 캐시를 넣었을 때 틀린 데이터가 보이는 상황은 어떻게 생기고 어떻게 막는가
- OAuth의 `state`와 PKCE는 각각 무슨 공격을 막는가
- 통합 테스트와 단위 테스트 중 어느 쪽에 더 투자해야 하는가, 이 프로젝트에선 왜 그런가
- NestJS의 의존성 주입이 없으면 Express에서 뭘 손으로 해야 하는가
- 배포 환경에서 쿠키가 안 붙을 때 확인할 순서는 무엇인가
