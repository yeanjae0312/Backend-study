## 0. 개요

### 목표

- 백엔드의 기본 동작(HTTP, DB, 인증, 테스트, 배포)을 **왜 그런지 설명할 수 있는 수준**으로 익힌다.
- NestJS로 기능 하나를 설계, 구현, 테스트, 배포까지 혼자 추가할 수 있다.
- 최종 산출물: 이메일 로그인 + 소셜 로그인이 되는 Nest API 서버, 이를 소비하는 최소 웹 화면, 나중에 모바일 앱.
- 매 단계에서 Spring Boot 대응을 기록해, Claude Code가 생성한 Spring 코드를 읽고 문제를 잡을 수 있게 한다.

## Phase 1. 원시 서버: `node:http` (3~5일)

### 목표

프레임워크 없이 HTTP 서버를 만들어, 이후 Nest가 "대신 해주는 것"이 무엇인지 기준점을 세운다.

학습 문서: `study-docs/01-raw-http/HTTP-기초.md`

### 작업

- [x] `node:http`로 서버 띄우기. 포트, 리스닝, 프로세스 종료(SIGINT) 처리 (2026-11-10, 01-raw-http/server.ts)
- [x] URL과 메서드로 분기하는 라우터를 직접 작성 (`GET /notes`, `POST /notes`, `GET /notes/:id`)
- [x] 요청 바디를 스트림으로 읽어 JSON 파싱. 잘못된 JSON이면 400 응답
- [x] 응답 헤더 직접 설정 (`Content-Type`, `Content-Length`), 상태 코드 선택 (200, 201, 204, 400, 404, 405, 500)
- [x] 메모리 배열에 데이터 저장 (DB 없이)
- [ ] 쿠키 읽기와 쓰기 (`Cookie`, `Set-Cookie` 헤더를 문자열로 직접 파싱)
- [x] 에러를 잡아 500으로 바꾸고 프로세스가 죽지 않게 하기
- [ ] 브라우저 HTML 한 장에서 `fetch`로 호출. CORS 에러를 일부러 내고 `Access-Control-*` 헤더로 해결
- [ ] curl 또는 REST Client로 모든 엔드포인트를 호출한 기록 남기기

### 익혀야 할 개념

- HTTP 메시지 구조: 시작줄, 헤더, 빈 줄, 바디
- 요청은 스트림이다. 바디는 한 번에 오지 않는다
- 상태 코드 분류 (2xx, 3xx, 4xx, 5xx)와 각 코드의 의미
- 멱등성: GET, PUT, DELETE는 멱등, POST는 아님
- 쿠키의 속성: `HttpOnly`, `Secure`, `SameSite`, `Path`, `Max-Age`
- 동일 출처 정책과 CORS, 프리플라이트(OPTIONS)
- 이벤트 루프: 동기 코드가 길면 서버 전체가 멈추는 이유 (Spring의 요청당 스레드 모델과의 차이)

### 완료 기준

- 라우팅, 바디 파싱, 쿠키, CORS를 라이브러리 없이 구현해서 브라우저와 curl 양쪽에서 동작한다.
- "Nest가 있으면 이 코드 중 어디가 없어지는가"를 목록으로 적었다. (HTTP-기초.md 11절)

### 함정

- 여기서 완성도를 높이려 하지 않는다. 지저분해도 된다. 목적은 기준점이다.

### 익혀야 할 개념

- 호이스팅과 유령 의존성, pnpm의 `node_modules/.pnpm` 구조
- `dependencies` / `devDependencies` / `peerDependencies`, `workspace:` 프로토콜
- `package.json`의 `main`, `exports`, `types`
- ESM과 CommonJS. Nest는 아직 CommonJS가 기본이라는 것
- 트랜스파일과 타입 검사와 번들은 다른 작업
- **Nest 핵심**: 모듈(경계), 컨트롤러(HTTP 입구), 프로바이더(로직), DI 컨테이너(누가 `new`를 하는가), 요청 라이프사이클 순서
- 데코레이터가 하는 일: 클래스에 메타데이터를 붙이고 Nest가 부팅 시 읽는다

### Spring에서는
- 모듈 ↔ `@Configuration` + 컴포넌트 스캔 (Spring은 패키지 단위 스캔이라 모듈 선언이 없음)
- 컨트롤러 ↔ `@RestController`, 서비스 ↔ `@Service`, 프로바이더 ↔ 빈(Bean)
- `@Injectable()` + 생성자 주입 ↔ 생성자 주입 (Spring도 생성자 주입이 권장)
- 미들웨어 ↔ 서블릿 필터, 가드 ↔ Spring Security 필터 / `@PreAuthorize`, 인터셉터 ↔ `HandlerInterceptor` / AOP, 파이프 ↔ `@Valid` + 컨버터, 예외 필터 ↔ `@RestControllerAdvice`
- `main.ts` ↔ `@SpringBootApplication` 클래스의 `main`
- Nest CLI `nest g` ↔ 없음. Spring은 IDE나 직접 작성

### 완료 기준

- 루트에서 `pnpm -r typecheck`, `pnpm --filter api start:dev`가 동작한다.
- 요청 하나가 미들웨어 → 가드 → 인터셉터 → 파이프 → 핸들러 → 인터셉터 → 예외 필터 순으로 지나는 로그를 직접 봤다.
- `NotesService`를 DI로 바꿔 끼워봤고, "Nest가 `new`를 대신 하는 이유"를 설명할 수 있다.

### 함정

- Turborepo는 아직 넣지 않는다.
- Nest CLI가 만들어준 파일을 "그냥 있는 것"으로 넘기지 않는다. 전부 열어본다.

## Phase 3. Nest로 메모 CRUD (3주)

### 목표

인증 없는 단순 리소스 하나로 Nest + DB + 검증 + 에러 + 테스트의 기본 흐름 전부를 겪는다. 이 Phase가 가장 중요하다.

### 작업

**3-1. DB 연결과 raw SQL (4일)**
- [ ] `docker-compose.yml`에 Postgres 추가, 볼륨 설정, 클라이언트로 접속
- [ ] `pg` 드라이버를 Nest 프로바이더로 등록 (`useFactory`로 풀 생성). 풀 크기를 1로 줄여 요청 두 개를 동시에 보내보기
- [ ] `notes` 테이블 설계: id(uuid), title, content, created_at, updated_at
- [ ] 마이그레이션 SQL 파일 직접 작성, 순서대로 적용하는 스크립트
- [ ] CRUD를 파라미터 바인딩(`$1`)으로. 문자열 연결로 SQL 인젝션을 재현하고 바인딩으로 막기
- [ ] 페이지네이션 offset → 커서. 정렬, 검색(`ILIKE`), `EXPLAIN ANALYZE`로 인덱스 전후 비교
- [ ] 트랜잭션: 메모 두 개를 한 번에 만들다 중간에 실패시켜 롤백 확인

**3-2. TypeORM 전환 (4일)**
- [ ] `@nestjs/typeorm` 설정, `Note` 엔티티(`@Entity`, `@Column`, `@CreateDateColumn`)
- [ ] 저장소 계층만 `Repository<Note>`로 교체. 서비스와 컨트롤러는 손대지 않는 게 목표
- [ ] TypeORM이 생성하는 SQL을 로깅으로 확인하며 raw SQL과 비교
- [ ] 마이그레이션을 TypeORM CLI로 전환. `synchronize: true`를 왜 운영에서 쓰면 안 되는지
- [ ] `QueryRunner`와 `DataSource.transaction`으로 트랜잭션

**3-3. 검증, 에러, 응답 형식 (4일)**
- [ ] `CreateNoteDto`에 class-validator 데코레이터, 전역 `ValidationPipe` (`whitelist`, `transform` 옵션의 의미)
- [ ] 에러 응답 형식 통일 (`{ code, message, details? }`). 전역 예외 필터, 커스텀 예외 클래스
- [ ] 404, 400(검증 실패), 409(중복), 500 각각 언제 쓰는지 정리
- [ ] 로깅 인터셉터 (메서드, 경로, 소요 시간)
- [ ] 응답 타입을 `packages/shared`에 두고 컨트롤러 반환 타입으로 사용

**3-4. 테스트 (5일)**
- [ ] Jest 설정 확인 (Nest CLI 기본), 단위 테스트: `Test.createTestingModule`로 `NotesService`에 가짜 Repository 주입
- [ ] e2e 테스트: testcontainers로 Postgres 띄우고 supertest로 각 엔드포인트 성공과 실패
- [ ] 테스트 DB 초기화 전략 (테스트마다 테이블 비우기 vs 트랜잭션 롤백)
- [ ] CI 없이도 `pnpm --filter api test`, `test:e2e` 한 번에 돌게

### 익혀야 할 개념

- 커넥션 풀, 풀이 바닥나면 생기는 일
- SQL 기본과 실행 계획, 트랜잭션과 ACID
- offset 페이지네이션이 느려지는 이유와 커서 방식
- ORM이 대신 해주는 것과 숨기는 것. 엔티티와 테이블의 관계
- 계층 분리의 목적: 교체 가능성과 테스트 가능성 (3-2에서 실제로 교체해봄)
- 검증은 경계에서 한 번. `whitelist`가 막는 공격(mass assignment)
- 단위 테스트와 e2e 테스트의 차이, DI가 테스트를 쉽게 만드는 방식

### Spring에서는
- `pg` 풀 ↔ HikariCP (Spring Boot 기본 커넥션 풀). `spring.datasource.hikari.maximum-pool-size`
- raw SQL ↔ `JdbcTemplate`
- TypeORM `@Entity` ↔ JPA `@Entity`, `Repository<Note>` ↔ `JpaRepository<Note, UUID>`, `@CreateDateColumn` ↔ `@CreatedDate` + Auditing
- `synchronize: true` ↔ `spring.jpa.hibernate.ddl-auto=update` (둘 다 운영 금지), 마이그레이션 ↔ Flyway / Liquibase
- `DataSource.transaction` ↔ `@Transactional` (Spring은 AOP 프록시라 **같은 클래스 안에서 호출하면 안 걸린다**는 함정이 있음)
- class-validator `@IsString()` ↔ `@NotBlank`, `ValidationPipe` ↔ `@Valid`
- 전역 예외 필터 ↔ `@RestControllerAdvice`
- `Test.createTestingModule` + 가짜 주입 ↔ `@MockBean` / Mockito, e2e ↔ `@SpringBootTest` + `MockMvc` / Testcontainers (Java에도 같은 이름의 라이브러리가 있음)

### 완료 기준

- 메모 CRUD + 페이지네이션 + 검색이 단위와 e2e 테스트로 덮여 있고 전부 통과한다.
- raw SQL → TypeORM 전환에서 서비스와 컨트롤러를 안 건드렸다.
- SQL 인젝션을 재현하고 막은 기록, mass assignment를 `whitelist`로 막은 기록이 있다.

### 함정

- 메모에 "작성자" 컬럼을 미리 넣지 않는다. Phase 4에서 필요가 생길 때 넣는다.
- TypeORM의 `relations`, `eager`, `lazy`는 여기서 건드리지 않는다. Phase 4에서 users ↔ notes 관계가 생길 때 본다.

## Phase 4. 인증 1차: 세션 쿠키를 가드로 (2주)

### 목표

"메모를 남이 못 보게 하려면 뭐가 필요한가"에서 출발해 세션 기반 인증과 권한을 **라이브러리 없이 Nest 가드로** 구현한다.

### 작업

**4-1. 사용자와 비밀번호 (3일)**
- [ ] `User` 엔티티: id, email(unique), passwordHash, createdAt
- [ ] argon2로 해싱. bcrypt와의 차이, 왜 SHA-256으로 하면 안 되는지
- [ ] 가입 API: 이메일 형식 검증, 중복 시 409, 비밀번호 최소 규칙
- [ ] 로그인 API: 이메일 없음과 비밀번호 틀림을 같은 메시지로 응답하는 이유

**4-2. 세션 (4일)**
- [ ] `Session` 엔티티: id(랜덤 토큰), userId, expiresAt
- [ ] 로그인 성공 시 세션 생성, `Set-Cookie` (`HttpOnly`, `SameSite=Lax`, 개발에선 `Secure` 제외). `cookie-parser` 미들웨어
- [ ] `AuthGuard`: 쿠키에서 세션 찾고 만료 확인, `request.user` 채우기. `@UseGuards()`로 라우트에 적용
- [ ] `@CurrentUser()` 커스텀 파라미터 데코레이터
- [ ] 로그아웃: 세션 삭제 + 쿠키 만료. 만료된 세션 정리 스크립트
- [ ] `GET /me`

**4-3. 권한 (3일)**
- [ ] `notes`에 `user_id` 추가 마이그레이션. 기존 데이터 처리 결정
- [ ] User ↔ Note 관계 (`@OneToMany`, `@ManyToOne`). N+1 재현 후 `relations` 또는 QueryBuilder 조인으로 해결
- [ ] 내 메모만 조회, 남의 메모 수정과 삭제는 403 vs 404 중 결정하고 이유 적기
- [ ] 공개 라우트와 보호 라우트를 `@Public()` 데코레이터 + 전역 가드로 구분

**4-4. 테스트와 보안 점검 (3일)**
- [ ] e2e에서 로그인 상태를 유지하는 헬퍼 (쿠키 전달)
- [ ] 가입, 로그인, 로그아웃, 남의 메모 접근 테스트
- [ ] 로그인 시도 레이트리밋 (`@nestjs/throttler`, 지금은 메모리 저장소)
- [ ] CSRF가 뭔지, `SameSite=Lax`가 어디까지 막는지 정리

### 익혀야 할 개념

- 인증(누구인가)과 인가(뭘 할 수 있는가)
- 비밀번호 해싱: 솔트, 느린 해시, 레인보우 테이블
- 세션 기반 인증의 흐름, 상태가 서버에 사는 것의 장단점
- 가드가 미들웨어와 다른 점: 핸들러 메타데이터(`Reflector`)를 읽을 수 있다
- 타이밍 공격과 응답 메시지로 정보가 새는 문제
- CSRF, XSS와 쿠키

### Spring에서는
- 직접 만든 `AuthGuard` ↔ Spring Security의 `SecurityFilterChain` + 커스텀 `OncePerRequestFilter`
- `@Public()` + 전역 가드 ↔ `http.authorizeHttpRequests(auth -> auth.requestMatchers("/login").permitAll().anyRequest().authenticated())`
- `@CurrentUser()` ↔ `@AuthenticationPrincipal`
- 세션 ↔ `HttpSession` + `JSESSIONID` (Spring Security가 기본으로 해줌. 회사 코드에서 `sessionManagement()` 설정 확인)
- argon2 ↔ `PasswordEncoder` (`BCryptPasswordEncoder`, `Argon2PasswordEncoder`)
- 403 vs 404 결정 ↔ `AccessDeniedHandler`
- `@OneToMany` N+1 ↔ JPA의 같은 문제. `fetch join`, `@EntityGraph`, `@BatchSize`

### 완료 기준

- 로그인 없이는 메모를 못 보고, 로그인하면 내 메모만 보인다. 전부 e2e로 증명한다.
- 세션 방식의 장단점과 "그럼 JWT는 언제 필요한가"에 가설을 적었다.

### 함정

- JWT, Passport는 아직 쓰지 않는다. Phase 7에서 손으로 짠 것을 Passport로 옮기며 비교한다.

## Phase 5. Nest 실무 기본기 (2~3주)

### 목표

운영 가능한 Nest 서버가 갖춰야 할 것들을 Nest 생태계의 공식 모듈로 하나씩 넣는다. 각각이 없을 때의 불편을 먼저 겪는다.

### 작업

**5-1. 설정 (2일)**
- [ ] `@nestjs/config` + 스키마 검증(Joi 또는 class-validator). 없으면 시작 시 바로 실패

**5-2. Redis (4일)**
- [ ] docker-compose에 Redis 추가, Redis 클라이언트를 프로바이더로
- [ ] 세션 저장소를 Postgres에서 Redis로 이동. TTL로 만료. 왜 옮기는지 적기
- [ ] `@nestjs/throttler`의 저장소를 Redis로
- [ ] `@nestjs/cache-manager`로 메모 목록 캐시와 무효화. 캐시 때문에 틀린 데이터가 보이는 상황을 일부러 만들기

- [ ] `enableShutdownHooks()`와 `OnModuleDestroy`로 graceful shutdown

**5-4. 문서와 헬스체크 (2일)**
- [ ] `@nestjs/swagger`: DTO 데코레이터로 문서 생성, Swagger UI
- [ ] `@nestjs/terminus`: `/health`에서 DB, Redis 확인

**5-5. Turborepo 도입 (1일)**
- [ ] `turbo.json`에 `dev`, `build`, `test`, `lint`. `dependsOn: ["^build"]` 의미
- [ ] shared를 바꿨을 때 api만 다시 돌아가는지 캐시 확인

### 익혀야 할 개념

- 12-factor: 설정은 환경 변수로, 로그는 stdout으로
- 인메모리 저장소가 필요한 이유 (속도, 만료, 여러 인스턴스 간 공유)
- 캐시 무효화가 어려운 이유, TTL과 명시적 무효화
- 구조화 로깅과 상관 관계 id
- Nest 라이프사이클 훅 (`OnModuleInit`, `OnModuleDestroy`, `OnApplicationShutdown`)

### Spring에서는
- `@nestjs/config` ↔ `application.yml` + `@ConfigurationProperties` + `@Validated`
- Redis 세션 ↔ Spring Session Data Redis (설정 몇 줄로 `HttpSession`이 Redis로 감)
- `@nestjs/cache-manager` ↔ `@Cacheable`, `@CacheEvict`
- `@nestjs/throttler` ↔ 내장 없음. Bucket4j 또는 게이트웨이에서
- `nestjs-pino` ↔ SLF4J + Logback, MDC로 request id
- `@nestjs/swagger` ↔ springdoc-openapi
- `@nestjs/terminus` ↔ Spring Boot Actuator `/actuator/health`
- 라이프사이클 훅 ↔ `@PostConstruct`, `@PreDestroy`

### 완료 기준

- Redis를 끄면 헬스체크가 실패하고, 환경 변수가 빠지면 서버가 시작 시 알려준다.
- `/docs`에서 모든 API를 볼 수 있다.
- Phase 3~4 테스트가 전부 그대로 통과한다.

## Phase 7. 소셜 로그인, Passport, 토큰, 작업 큐 (3주)

### 목표

외부 인증 제공자 연동을 손으로 한 번 하고 Passport로 옮기며, 세션을 토큰 기반으로 확장하고, 요청 밖에서 도는 작업을 다룬다.

### 작업

**7-1. Google OIDC 수동 구현 (4일)**
- [ ] Google Cloud Console에서 OAuth 클라이언트 생성, 리다이렉트 URI 등록
- [ ] 인가 코드 흐름을 라이브러리 없이: `/auth/google` → 구글 → `/auth/google/callback`
- [ ] `state`로 CSRF 방지, PKCE 적용
- [ ] 코드를 토큰으로 교환, `id_token` 서명 검증 (JWKS)
- [ ] `OAuthAccount` 엔티티: provider, providerUserId, userId. 같은 이메일의 기존 계정과 연결 정책 결정
- [ ] 소셜 로그인 후에도 기존 세션 방식으로 로그인 유지

**7-2. Passport 전환 (3일)**
- [ ] `@nestjs/passport` + `passport-google-oauth20`로 7-1을 다시 구현. `PassportStrategy` 클래스, `AuthGuard('google')`
- [ ] 로컬 로그인도 `passport-local` 전략으로. Phase 4의 직접 만든 가드와 비교표 작성
- [ ] 무엇이 사라지고 무엇이 숨겨졌는지 적기

**7-3. 액세스 + 리프레시 토큰 (5일)**
- [ ] `@nestjs/jwt`로 액세스 토큰(짧은 만료), 리프레시 토큰(불투명, DB 저장, 긴 만료)
- [ ] `passport-jwt` 전략으로 `AuthGuard('jwt')`. 세션 가드와 공존 (웹은 쿠키 세션, 앱은 Bearer)
- [ ] 리프레시 토큰 회전과 재사용 탐지 (훔친 토큰이 쓰이면 전체 무효화)
- [ ] 기기별 로그아웃, 전체 로그아웃

**7-4. BullMQ 작업 큐 (3일)**
- [ ] `@nestjs/bullmq`로 가입 시 이메일 인증 발송을 큐에. 실제 발송은 Mailpit 컨테이너
- [ ] `@Processor` 워커를 별도 프로세스로 실행
- [ ] 실패 재시도, 지수 백오프, 죽은 작업 확인
- [ ] 이메일 인증 토큰 검증 엔드포인트

### 익혀야 할 개념

- OAuth 2.0과 OIDC의 차이, 인가 코드 흐름의 각 단계
- `state`와 PKCE가 막는 공격
- Passport의 전략 패턴: `validate()`가 하는 일과 `request.user`에 들어가는 것
- JWT 구조, 서명 검증, 왜 JWT를 세션처럼 무효화하기 어려운지
- 리프레시 토큰 회전과 재사용 탐지
- 요청 응답 밖에서 처리해야 하는 일과 큐, 멱등한 작업과 재시도

### Spring에서는
- 수동 OIDC ↔ 거의 안 함. `spring-boot-starter-oauth2-client` + `application.yml`의 `spring.security.oauth2.client.registration.google`
- Passport 전략 ↔ `OAuth2UserService`, `AuthenticationProvider`
- `@nestjs/jwt` + `passport-jwt` ↔ `spring-boot-starter-oauth2-resource-server` 또는 jjwt + 커스텀 필터
- `AuthGuard('jwt')` ↔ `JwtAuthenticationFilter extends OncePerRequestFilter` + `SecurityContextHolder`
- BullMQ ↔ `@Async` + `@Scheduled`(단순), Spring Batch, 또는 RabbitMQ/Kafka 연동
- Mailpit ↔ 같은 걸 씀. `JavaMailSender`

### 완료 기준

- 구글 로그인과 이메일 로그인이 같은 사용자로 연결된다.
- 직접 구현과 Passport 버전의 비교표가 있다.
- 토큰 재사용 공격을 e2e로 재현하고 막는다.
- 워커를 꺼도 api는 동작하고, 켜면 밀린 작업이 처리된다.

### 함정

- 구글 하나만 한다. 두 번째 제공자는 전략 클래스 하나 추가다.

## Phase 8. Nest 실무 심화 (2~3주)

### 목표

지금까지 만든 것을 실무 코드베이스처럼 다듬으며, Nest 고유의 설계 도구와 테스트 전략을 익힌다. 재구현이 아니라 리팩토링이다.

### 작업

**8-1. 모듈 설계 (4일)**
- [ ] 모듈 경계 점검: `AuthModule`, `UsersModule`, `NotesModule`, `SessionsModule`이 서로 뭘 export하고 import하는지 그림으로. 순환 의존(`forwardRef`)이 생겼다면 왜인지
- [ ] 동적 모듈: `RedisModule.forRoot(options)` 직접 만들어보기. `@nestjs/typeorm`의 `forRoot`가 하는 일이 이것
- [ ] 커스텀 프로바이더 토큰(`@Inject('REDIS')`)과 인터페이스 기반 주입

**8-2. 트랜잭션과 도메인 (3일)**
- [ ] 서비스 계층 트랜잭션 패턴 정리: `DataSource.transaction` 콜백 vs 데코레이터 라이브러리 vs CLS. 하나 고르고 이유
- [ ] 엔티티에 로직을 두는 것과 서비스에 두는 것의 경계 결정

**8-3. 테스트 전략 (3일)**
- [ ] 단위 테스트에서 DI 모킹 패턴 정리 (`useValue`, `jest.fn()`, 부분 모킹)
- [ ] 가드, 인터셉터, 파이프의 단위 테스트
- [ ] 테스트 피라미드: 이 프로젝트에서 단위 vs e2e 비율을 어떻게 가져갈지 결정

**8-4. 비교와 정리 (3일)**
- [ ] Prisma 하루: 메모 모듈만 Prisma로 옮겨보고 TypeORM과 비교표
- [ ] **Nest ↔ Spring 대응표 완성** (부록 D의 표를 각 Phase 기록으로 채운다)
- [ ] "회사 Spring 코드에서 이 구조를 어디서 봤는가"를 항목마다 적기

### Spring에서는
- 동적 모듈 `forRoot` ↔ `@EnableXxx` + `@ConfigurationProperties` (Spring Boot 자동 설정)
- 커스텀 토큰 주입 ↔ `@Qualifier`
- `forwardRef` 순환 의존 ↔ Spring도 생성자 주입 순환은 금지. `@Lazy`
- 트랜잭션 패턴 ↔ `@Transactional` 전파 속성 (`REQUIRED`, `REQUIRES_NEW`)
- Prisma ↔ 가까운 게 없음. 굳이 하면 jOOQ

### 완료 기준

- 모듈 의존 그림이 있고 순환이 없다.
- Nest ↔ Spring 대응표가 모든 Phase 항목으로 채워져 있다.
- 새 기능(예: 메모 태그)을 설계부터 테스트까지 혼자 추가해봤다. **이것이 6개월 목표의 핵심 판정이다.**

## Phase 9. 배포와 운영 (1~2주)

### 목표

로컬에서만 돌던 서버를 실제 환경에 올리고, 운영 중 보는 것들을 경험한다.

### 작업

- [ ] api용 Dockerfile (멀티 스테이지: 의존성 → `nest build` → 실행). `pnpm deploy` 또는 `turbo prune`으로 모노레포에서 api만 추리기
- [ ] 로컬에서 이미지로 실행해 docker-compose의 Postgres, Redis와 연결
- [ ] Postgres 호스팅 (Neon 또는 Supabase), Redis 호스팅 (Upstash)
- [ ] Fly.io 또는 Railway에 api 배포, 환경 변수 주입, 마이그레이션 실행 시점 결정
- [ ] 웹을 Vercel에 (루트 디렉터리 `apps/web`). 운영 도메인에서 쿠키와 CORS 다시 맞추기 (`Secure`, 도메인)
- [ ] 헬스체크를 플랫폼에 연결, 로그 확인
- [ ] autocannon으로 부하를 걸어 커넥션 풀 크기와 인덱스 유무에 따른 응답 시간 비교
- [ ] 롤백 방법 정리

### Spring에서는
- `nest build` 산출물 ↔ `gradle bootJar`의 fat jar. Dockerfile 구조는 거의 같음
- 마이그레이션 시점 ↔ Flyway는 앱 시작 시 자동 실행이 기본. 그게 위험한 이유도 같음
- Actuator ↔ terminus

### 완료 기준

- 공개 URL에서 가입, 로그인, 구글 로그인, 메모 작성이 된다.
- 부하 테스트 전후 수치를 기록했다.

## 부록 B. 끝났을 때 설명할 수 있어야 하는 질문

- 요청 하나가 브라우저에서 출발해 Nest의 미들웨어, 가드, 인터셉터, 파이프, 핸들러를 지나 DB를 거쳐 응답으로 돌아오기까지 각 단계에서 무슨 일이 일어나는가
- Nest가 `new`를 대신 하는 이유와, 그게 테스트에서 어떤 이득이 되는가
- 세션과 JWT는 각각 언제 쓰고, 왜 JWT는 무효화가 어려운가
- 커넥션 풀이 없으면 무슨 일이 생기는가
- 인덱스는 왜 모든 컬럼에 걸지 않는가
- 캐시를 넣었을 때 틀린 데이터가 보이는 상황은 어떻게 생기고 어떻게 막는가
- OAuth의 `state`와 PKCE는 각각 무슨 공격을 막는가
- Passport의 `validate()`가 반환한 값은 어디로 가는가
- 단위 테스트와 e2e 테스트 중 어느 쪽에 더 투자해야 하는가, 이 프로젝트에선 왜 그런가
- 배포 환경에서 쿠키가 안 붙을 때 확인할 순서는 무엇인가
- (Spring) 회사 코드에 `async`가 없는 이유와, 그 대신 서버 전체가 느려지는 상황은 무엇인가
- (Spring) `@Transactional`이 같은 클래스 안에서 호출하면 안 걸리는 이유는 무엇인가

### Nest ↔ Spring 대응 요약표 (학습하며 채워 나간다)
| 개념 | NestJS | Spring Boot | Express (참고) |
|---|---|---|---|
| 진입점 | `NestFactory.create` → `listen` | `SpringApplication.run` | `express()` → `listen` |
| 라우팅 | `@Controller`, `@Get()` | `@RestController`, `@GetMapping` | `app.get()` |
| 경로 변수 / 쿼리 | `@Param`, `@Query` | `@PathVariable`, `@RequestParam` | `req.params`, `req.query` |
| 바디 | `@Body()` + DTO | `@RequestBody` + DTO | `express.json()` + `req.body` |
| 검증 | class-validator + `ValidationPipe` | `@Valid` + Bean Validation | 수동 또는 라이브러리 |
| 계층 | Controller → Service → Repository | `@RestController` → `@Service` → `@Repository` | 수동 분리 |
| DI | `@Injectable()`, 모듈 프로바이더 | `@Component`, 생성자 주입 | 없음 |
| 모듈 | `@Module({ imports, providers, exports })` | 패키지 스캔 + `@Configuration` | 없음 |
| 미들웨어 | `NestMiddleware` | 서블릿 `Filter` | `app.use()` |
| 인증 | 가드, Passport 전략 | `SecurityFilterChain`, `@PreAuthorize` | 미들웨어 |
| 횡단 관심사 | 인터셉터 | `HandlerInterceptor`, AOP | 미들웨어 |
| 에러 통일 | 예외 필터 | `@RestControllerAdvice` | 에러 미들웨어 |
| ORM | TypeORM `@Entity`, `Repository` | JPA `@Entity`, `JpaRepository` | 직접 선택 |
| 트랜잭션 | `DataSource.transaction` | `@Transactional` | 직접 |
| 설정 | `@nestjs/config` | `application.yml` + `@ConfigurationProperties` | `process.env` |
| 캐시 | `@nestjs/cache-manager` | `@Cacheable` | 직접 |
| 문서 | `@nestjs/swagger` | springdoc-openapi | 직접 |
| 헬스체크 | `@nestjs/terminus` | Actuator | 직접 |
| 테스트 | Jest + `Test.createTestingModule`, supertest | JUnit + `@SpringBootTest`, MockMvc | Jest + supertest |
| 빌드 | `nest build` (tsc) | Gradle `bootJar` | tsc / tsx |
| 동시성 모델 | 단일 스레드 + 이벤트 루프 | 요청당 스레드 (풀) | 단일 스레드 + 이벤트 루프 |
